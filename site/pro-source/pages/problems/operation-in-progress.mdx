## When it occurs

Another attempt of the same operation holds a live lease, so this request did not run the handler.

## Client handling

Retry later with the same key and the same request, after the `Retry-After` delay when present. Do not switch to a new key: that could run the operation twice.

## Server correction

Check the attempt holding the lease. Do not start the same operation under another key while that attempt can still send.

## Response fields

### Execution middleware

- `type` (string, always): The exact type URI above.
- `title` (string, always): The HTTP status text.
- `status` (integer, always): The HTTP status of the response.
- `code` (string, always): The stable code above.
- `operation_ref` (string, always): An opaque reference to the operation. It is set only after `ReplayCheck` allows the request, and is empty when no operation was found. Use it to look up the operation; it does not grant access.
- `operation_state` (string, always): `started`, `uncertain`, `completed` or `failed`; empty when no operation was found.
- `safe_new_key` (boolean, always): `true` only when the client may retry with a new key. It is always `false` when `operation_ref` and `operation_state` are empty.

Headers:

- `Cache-Control` (always): `no-store` on every execution problem.
- `Retry-After` (conditional): The lease's remaining time in whole seconds, rounded up. Sent when it is positive.

Notes:

- Execution removes any `Idempotent-Replayed` header from problem responses.
