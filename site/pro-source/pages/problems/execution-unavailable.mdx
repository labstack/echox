## When it occurs

Execution could not use its store, or another error stopped it before the handler ran. The handler did not run for this request.

## Client handling

Retry later with the same key and request, after the `Retry-After` delay. Do not switch to a new key: an earlier attempt under this key may exist.

## Example response

The package may omit diagnostic text or return it empty. Operation references do not grant access. Custom handlers can replace the body.

## How to fix

Restore journal storage and inspect the original operation key before continuing. Retry only according to the execution answer and retained ID. An unavailable store cannot prove an external send failed.

## Response fields

### execution middleware

- `type` (string, always): The exact type URI above.
- `title` (string, always): The HTTP status text.
- `status` (integer, always): The HTTP status of the response.
- `code` (string, always): The stable code above.
- `operation_ref` (string, always): Reference to the operation, shown only after replay authorization. Empty when no operation was found. The reference helps locate the operation. It does not authorize access.
- `operation_state` (string, always): `started`, `uncertain`, `completed` or `failed`; empty when no operation was located.
- `safe_new_key` (boolean, always): True only when a new key is safe. Empty operation fields never allow a new key.

Headers:

- `Cache-Control` (always): `no-store` on every execution problem.
- `Retry-After` (always): Always `1`.

Notes:

- `operation_ref`, `operation_state` and `safe_new_key` are always present, even when empty or false. `Idempotent-Replayed` is removed. The body ends with a newline. HEAD responses have no body.
- Replay returns stored responses unchanged, including problem responses. Execution does not reclassify or translate them. Only headers listed in `ReplayHeaders` are replayed. Replay adds `Idempotent-Replayed: true`.
