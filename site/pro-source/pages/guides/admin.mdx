## When to use this guide

Use these tasks to mount the embedded console behind your application's authentication. [Install Echo Pro](/pro/install/) and construct the store or limiter each panel needs. Run console examples with:

```sh file=site/pro-source/examples/site-docs/commands.sh#test-admin
```

The [admin overview](/pro/admin/) explains sessions, access checks and audit recording. The [reference](/pro/reference/admin/) lists shell and panel configuration fields.

## Mount a read-only quota panel

Construct `quotaadmin.New` with the existing limiter. Map a validated session to a Viewer principal and a tenant allowlist. The example uses a random fixture session and shows final route verification:

```go file=site/pro-source/examples/source/admin/example_test.go
```

Replace the fixture `Authenticate` callback with your login check or an `authbind` mapping. Populate `Session` from that login's session ID. A fixed application-wide session cannot represent separate browser logins. Header-only credentials use `HeaderCredential` as in the complete [read-only example](/pro/admin/).

Register the remaining application routes, then call `VerifyRoutes` before serving. Keep the console prefix reserved. Set `PublicPath` if a reverse proxy serves the console under another path. Set `Origins` to your exact deployment origins.

## Add execution, audit or webhook panels

Pass a journal operator to `executionadmin`. Pass an authorized `audit.Reader` to `auditadmin.NewPanel`. A webhook panel needs `*webhookpg.Store` and global scope. The memory webhook store cannot back that panel.

The [full console tutorial](/pro/recipes/admin-demo/) shows the complete wiring and the PostgreSQL prerequisites. Close pools only after workers and in-flight console reads stop. Durable audit needs its separate PostgreSQL roles. Without them, the demo falls back to memory audit.

## Enable mutations deliberately

Enable the specific panel action, then grant the required Operator role and scope. Configure audit and signing keys before mounting write actions. Keep previews, typed confirmations, acknowledgements and required reasons. Preserve action IDs and business inputs across retries.

Enable credit actions with `EnableCredits` and destructive partition resets with `EnableReset`. Configure each action's role, reason and confirmation requirements before mounting. A reset clears every subject in the partition. Its preview records the expected reset generations; a later reset makes those generations stale. Execution resolution and uncertain webhook decisions require verified provider records. An HTTP timeout does not prove that a provider did nothing. Use the same action ID when you retry an action with an unknown result.

This executable credit fixture calls the actual preview and commit protocol. It explicitly opts out of audit for disposable local state. Replace that opt-out with a durable audit sink in a deployment. It prints the HTTP status, new balance, whether the credit applied, and audit outcome: `200 10 true applied`:


## Test the principal and protocol

Build a tenant-scoped test principal without global or reveal permission:

```go file=site/pro-source/examples/source/admin/admintest/example_test.go#ExampleTenantPrincipal
```

Exercise both permitted and denied views. Test revoked access on continuation and receipt replay. Check that the console checks access before it reports a malformed target. For mutations, assert that preview performs no effect and a failed audit intent performs no mutation.

Handle [admin unauthenticated](/pro/problems/admin-unauthenticated/) by obtaining a valid login. Handle [CSRF invalid](/pro/problems/admin-csrf-invalid/) by refreshing controls in the current session. On [admin timeout](/pro/problems/admin-timeout/), narrow an expensive read; after a mutation, reread state before choosing another action. The [problem catalog](/pro/problems/) distinguishes these cases.
